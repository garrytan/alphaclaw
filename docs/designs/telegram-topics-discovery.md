## Vision

### 10x Check
Topic knowledge stops being a launch-day snapshot and becomes a self-maintaining
channel-knowledge system: topics discover themselves from traffic the moment they
receive a message, arrive pre-named via a gateway hook when created, get named by
the agent when the hook missed them, show their health in the UI, get marked stale
when Telegram reports them gone, and notify the operator as the registry evolves.

## Baseline (Approach B — chosen over A/C, see Scope Decisions)
Six components, each detailed in the implementation plan:
1. **Traffic discovery** — unknown `(groupId, threadId)` pairs seen in session keys
   (usage/status labelers) are upserted into the registry as discovered/unnamed.
2. **Always-on guidance** — the TOOLS.md Topic Registry section + Sync Rules render
   even with zero topics (today an empty registry renders nothing).
3. **CLI fix + topic create** — `alphaclaw telegram topic add` is broken in Telegram
   multi-account mode (reads only legacy `channels.telegram.groups`, writes the wrong
   config branch, wrong baseUrl on prompt re-sync); fix it, and add
   `alphaclaw telegram topic create` so the agent can create+register topics itself.
4. **Native openclaw topic actions** — config sync enables
   `channels.telegram.actions.createForumTopic/editForumTopic` (operator-false preserved).
5. **Reconcile/mark-stale** — Telegram Bot API cannot list topics, so prune works by
   probing registered threads and catching "message thread not found" errors (the
   existing `isMissingTopicError` pattern from the delete route). Policy:
   **mark-stale on probe failure, never hard-delete**; operator confirms removal in UI.
6. **UI badges** — discovered/unnamed and stale badges in Manage Topics.
